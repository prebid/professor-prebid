# Prebid metadata extractors

These generate the lookup tables the **Pre-Auction** tab uses to attribute EIDs, network requests and
ortb2 enrichment to the prebid module that produced them. All read `node_modules/prebid.js` — no
network access.

Re-run them after bumping the `prebid.js` dependency. Each writes its `.ts` file directly and is
idempotent — running twice produces identical output:

```sh
node utils/prebidMetadata/extractEidSources.mjs      # -> src/pages/Shared/components/preAuction/eidSources.ts
node utils/prebidMetadata/extractProviderHosts.mjs   # -> src/pages/Shared/components/preAuction/providerHosts.ts
node utils/prebidMetadata/extractProviderSignals.mjs # -> src/pages/Shared/components/preAuction/providerSignals.ts
```

## How they work

`metadata/modules/*.json` in prebid.js is autogenerated by prebid's own `gulp update-metadata` and
carries the authoritative `componentName` for each `userId` and `rtd` module — the same name used in
`userSync.userIds[].name` and `realTimeData.dataProviders[].name`.

- **extractEidSources** joins that with the `source:` literals in `modules/*IdSystem.js` and the
  libraries they import. One module can own many sources.
- **extractProviderHosts** joins it with every URL literal in the module source plus the vendor's
  `disclosureURL`, reduced to registrable domains.
- **extractProviderSignals** records where each RTD module *writes* its contribution, from three
  sources: the module source, the module's `.md` (for shim modules that contain no path themselves),
  and a small curated map for vendors whose key exists only in their payload. RTD providers
  load a vendor payload script, but the enrichment is written by prebid's own module at a fixed path
  — `deepSetValue(bid, '<path>', data)`. The vendor supplies the value; the path is in the source,
  and finding a value there proves the data reached the auction.

**scanVendorPayloads** is a discovery aid, not part of the build. Several RTD modules merge whatever
their vendor payload script returns, so the ortb2 path exists nowhere in prebid's source:

```
someRtdProvider.js            const SCRIPT_URL = 'https://vendor.example/prebid/rtd.js'
vendor.example/prebid/rtd.js  g[Fd]({ortb2:{ext:{vnd:h}}})
```

That namespace key exists only in the payload, never in prebid's executable source. The scanner
fetches those payloads and reports the ortb2 paths it finds — the literal handed back to prebid has
to be in the shape prebid expects, so the property names usually survive minification. Only where a
payload builds its path dynamically does it come up empty, and that is when a live observation gets
curated into `MANUAL_ORTB2`. It needs network access, writes no file, and never executes what it
downloads.

## Known gaps

- A few id modules declare their source through a constant rather than a `source:` literal, so the
  scan sees a variable name and no quoted string. Their values live in
  the `MANUAL` map at the top of `extractEidSources.mjs`, and the script prints which modules it
  filled in. When bumping prebid.js, grep each of those modules for `source:` and follow the constant
  to confirm the value is still right — and check whether any *other* module has started doing the
  same, in which case it will silently go missing.
- Documentation links and shared infrastructure (`amazonaws.com`, `gstatic.com`, `doubleclick.net`,
  …) are excluded from the host map. A missing attribution is better than a wrong one.
- Modules that take their endpoint from publisher config cannot be covered
  statically; those hosts are read from the live config at runtime instead.
- Only writes count as a signal. Reading a path is not evidence that the module set it; counting a
  read would mark a provider landed on any page where prebid itself writes that path. Comments are
  stripped for the same reason: documentation carries names the code never emits.
- Paths that every adUnit carries (`ext`, `ext.data`) are excluded — they would match everything. The
  runtime check drops prebid's own writes (`ext.gpid`, `ext.tid`, `ext.data.adserver`) separately, so
  the "unattributed writes" list stays actionable.
- Around 40 RTD modules contribute only through global `ortb2`, whose segment names are usually built
  from publisher config rather than written as literals. Those still fall back to name-token matching
  and remain `unknown` when nothing matches.
- Three indirections are resolved, all found by running against a live page. Each was silently
  dropping a module before it was handled:
  - **constants** - `const NAME = '<domain>'` then `name: NAME` (5 modules)
  - **local aliases** - `const ortb2 = bidConfig.ortb2Fragments?.global` then a write through `ortb2`
    (`im`, whose `user.ext.data.im_segments` was invisible)
  - **EIDs from RTD modules** - three publish a `user.ext.eids` source as well as, or instead of, a
    segment. Without this they read as an unconfigured identity module.
- Some submodules are pure shims: they pass `reqBidsConfigObj` to a vendor payload and hold no path,
  so prebid's source holds no path. It is read from the module's `.md` at build time, and can usually
  be confirmed against the payload itself with `scanVendorPayloads.mjs`. Documentation can be stale,
  so treat a docs-derived path as a claim to check against a live auction rather than a fact.
